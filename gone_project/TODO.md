# GONE — Project outcomes

## Previously delivered before the approved account upgrade
- [x] **Clean, empty personal tracker:** New users start with no seeded/sample transactions; users can add and remove money-in and money-out entries, set or remove a savings goal, and see current-month received/spent totals and goal progress.
- [x] **Local-only data boundary:** Persist information in the same browser profile; no Manus Server, managed MySQL, real account authentication, or cross-device sync. Warn that anyone with access to that browser profile may see its entries.
- [x] **Warm-earth palette and static deployment:** Keep the approved deep-espresso, camel, terracotta, dusty-rose, and muted-olive colors; retain dependency-light GitHub/Vercel static hosting.

## Completed earlier request (local-only predecessor; retained for history)
- [x] **Welcome and onboarding:** First-time visitors see the GONE welcome screen with “Know where it went.” and a “Get started” path. Optional setup stores the local display name, monthly budget, and selected daily reminders; “Start with an empty ledger” skips setup. Setup completion stays in this browser. There is no password sign-up/login or claim of a secure account.
- [x] **Working navigation:** Routes work between Home, Add, Entries, Insights, Savings, and Split; navigation displays the active route, supports browser back/forward and static-host refreshes, and keeps one add action available throughout the app screens. On route changes, keyboard focus moves to the main screen and an accessible live region announces its title.
- [x] **Functional daily reminders:** Optional Chai ₹20, Metro ₹50, and Recharge ₹99 templates are not transaction history until used. Toggling one on creates one dated spending entry; toggling it off removes that reminder-generated entry; “Skip all today” skips unmarked reminders. Unmarked reminders auto-log at midnight while the page is open, or on return for the immediately previous day if the page was closed; auto-logged entries are labeled.
- [x] **App screens and forms:** Home shows a neutral time-based greeting, budget-left progress, spent-today/spent-this-week/biggest-expense summaries, daily reminders, and recent entries. Home “See all” opens Entries filtered to the last 7 days. Add supports spending (`title`, `amount`, `category`, `date`) and received money (`source`, `amount`, `date`); `5000` formats as `5,000`. Entries can be filtered by category and date range. Insights shows category, seven-day, and monthly summaries in CSS chart areas with `chart-category`, `chart-trend`, and `chart-monthly` mount IDs. Savings supports `target_amount`, recurring `monthly_income`, `bonus_amount`/`bonus_source`, and goal progress; its savings chart exposes `chart-savings-trend`, “View expenses” opens the last 7 days, and “Adjust goal” focuses the goal form. Split accepts `total_amount`, comma-separated `friends`, and `description`, calculates equal shares, and stores the result locally.
- [x] **Distinctive typography:** Self-host the clean Manrope variable font with its SIL Open Font License and use it throughout while preserving the approved warm-earth palette.
- [x] **Preserve local data:** Migrate existing local ledger entries and savings goal to the expanded browser schema; first-time users still begin with no sample transactions. Keep all app data in this browser profile without a server, real login, or cross-device sync.


## Approved Phase 2 — GONE ID accounts (local clone only)
- [x] **Registration and unique GONE ID:** Each registered user receives a GONE ID that is unique across the complete database (example `GONE-MH7K29`). Let users choose an ID where practical; reject duplicates with “This GONE ID is already taken. Please choose another.” Explain “Your GONE ID is unique across GONE.” and “Use it to sign in to your GONE account.” Do not require Gmail or a phone number. The user can view and copy their GONE ID later from Account details/Profile. If a chosen ID is taken, explain that an existing user should sign in and let a new user choose another or explicitly switch to a generated ID.
- [x] **Secure password login:** Register and sign in with GONE ID plus password. Store only a secure password hash; never return or log plaintext passwords or password hashes. A GONE ID is an identity, not a password, and knowing it must not grant financial-data access.
- [x] **First-run feature tour:** After the user completes or skips account setup, show a short three-step tour of the Home budget view, recurring reminders/Entries, and Insights/Savings/Split before allowing the first visit to Home; let the user advance or skip, and persist completion to that account.
- [x] **Two-question GONE ID recovery:** Require exactly two different questions selected from a controlled list. Explain “Choose questions whose answers only you are likely to know.” Normalize and securely hash both answers. Recovery must ask and verify both answers before showing the associated GONE ID; failures must not reveal another user’s information. Add practical attempt protection/rate limiting.
- [x] **User activity:** Record account creation and `last_active`; support total registered, new-today, new-this-week, active-today, and active-over-seven-days counts. Clearly distinguish registered users from active users; do not count simple page reloads as meaningful activity or label all registered users as live.
- [x] **Server-enforced data isolation and sessions:** Associate each user’s existing profile, transactions, reminders, and splits with the authenticated database user. Filter every private read/write/export/chart path by the session owner; changing a GONE ID in the client must not grant access. Do not expose session tokens in the UI; clear authentication state on logout. Preserve existing records and localStorage; do not silently assign unowned records to the first new account.
- [x] **Provider/deployment boundary:** Keep local development functional with local SQLite and prepare `DATABASE_URL` support for the user-selected Supabase Postgres provider. Do not deploy or push this local-only work. Production account behavior remains blocked until Supabase is securely connected and the Vercel environment is configured with durable database credentials.
- [ ] **Live production provisioning (blocked):** Supabase authorization has not been completed. Do not deploy account APIs until the user connects the selected Supabase project and configures durable server-side `DATABASE_URL`, `SECRET_KEY`, `DEBUG=False`, and allowed/CSRF origins in Vercel.

**Phase boundary:** Do not implement the Phase 3 five-minute setup expansion or Phases 4–10 (recurring income/payments/expenses, dashboard redesign, transaction learning/input redesign, savings/insights expansion, or light/dark/system theme). The latest user request authorizes only the existing account setup flow plus this short first-run feature tour before Home.
